## What was added in the latest pass (bidirectional SQLite ↔ Firestore sync)

1. **Changeset-based bidirectional sync** — `backend/src/sync-firestore.js` (`npm run sync:firestore`): every dataset is canonicalized to a common shape on both sides (so a row is the same row on SQLite and Firestore, with the driver's `''`/`null` unset equivalence baked in), then a per-row diff produces two write plans (`toLocal`, `toRemote`). Both directions converge to the same state except for rows deliberately left divergent.
2. **Conflict-aware resolution** — per-row policies: `last-write-wins` (default, newest timestamp), `keep-sqlite`, `keep-firestore`, `skip` (leave both sides as-is and report). Passwords are redacted from conflict reports.
3. **Deletion semantics** — `ignore` (default) is a union merge: rows seen on either side are kept on both, presence-only rows reported as candidates. `propagate` (one-way `--direction` only) makes the plan a mirror: absent rows are dropped from the target (products soft-deleted on SQLite, never hard-deleted; locations never auto-deleted).
4. **Scope** — products, inventory (per-location stock), stock movements, order inquiries, users, sales, alerts between `backend/data/inventrak.db` and Firestore; the npm-free JSON-file mode is ephemeral and not synced. CLI flags: `--dry-run`, `--direction=both|to-firestore|to-sqlite`, `--conflict=…`, `--deletions=propagate`.
